# HI, JACK LIVE

**Единый паспорт проекта, архитектурные правила и дорожная карта до версии 1.0**  
**Редакция документа:** 1.0 от 11 ноября 2026 года  
**Назначение:** постоянный файл знаний проекта ChatGPT и точка входа для отдельных чатов разработки модулей.

> **Статус документа:** согласованная целевая архитектура и перечень требований. Формулировки «должно» обозначают требования, а не подтверждение реализации. Фактическая готовность определяется только тестами, результатами сборок и подтверждёнными проверками оператора.

## 1. Миссия и текущее состояние

**HI, JACK LIVE 1.0** — локальное Windows-приложение для подготовки и управления графикой покерной трансляции Hi, Jack Club, работающее совместно с OBS Studio. Приложение должно быть пригодно для реального эфира, масштабироваться независимыми модулями и в дальнейшем поддерживать компьютерное зрение, ИИ-комментатора и автоматическое создание клипов.

**Зафиксированная контрольная точка на 11.11.2026:** проверка версии **v0.3.4**. Базовая архитектура существует по результатам предшествующей разработки, однако стабильность Windows-приложения ещё **не подтверждена**. По результатам пользовательского тестирования отмечались зависания интерфейса даже при обычном взаимодействии с окном. Ближайшая цель — довести стабильную основу, настройку плашек, турнирного таймера и отображения времени до подтверждённой работоспособности, затем перейти к независимой разработке модулей.

**Состояние GitHub:** основным обсуждавшимся репозиторием приложения является `AIestimGRO/hjVISION` (`https://github.com/AIestimGRO/hjVISION`). При проверке 11.11.2026 он возвращал состояние пустого Git-репозитория. Это лишь снимок на дату проверки: наличие локальных исходников и более поздних изменений должно проверяться отдельно. Репозиторий обучающих данных `hi-jack-ai-training` задан как архитектурное требование, его создание и наполнение нельзя считать подтверждённым без проверки.

### Правило трактовки статусов

- **Подтверждено:** проверено в работающей Windows-сборке или подтверждено результатом автоматизированного теста, соответствующим конкретному требованию.
- **В коде:** реализация присутствует в проверяемом коммите, но ещё не прошла нужную ручную/интеграционную проверку.
- **В работе:** есть план, прототип или незавершённая разработка.
- **Запланировано:** зафиксировано в ТЗ, но реализация не подтверждена.
- **Неизвестно:** нет достаточных данных; не подменять статус догадками и процентами.

## 2. Основные архитектурные решения

1. **OBS Studio остаётся центром видео и аудио:** захват камер, микширование, запись и трансляция выполняются средствами OBS. HI, JACK LIVE не подменяет OBS и взаимодействует с ним через браузерные источники и, по мере готовности, `obs-websocket`.
2. **Windows-приложение работает локально:** управление, данные эфира, настройки и API-ключи располагаются на компьютере оператора. Локальный сервер должен иметь контролируемый жизненный цикл, диагностику и восстановление после сбоев.
3. **Модульность — обязательное свойство, а не только структура папок:** функциональные области имеют собственный каталог, версию, манифест, документацию, тесты, явные входные точки и согласованные публичные контракты с HI, JACK CORE.
4. **Независимые обновления:** если совместимость соблюдена, оператор может заменить только нужный модуль из ZIP; остальные модули и пользовательские данные не затрагиваются. Неудачное обновление откатывается.
5. **Граница данных и кода:** исходники и ресурсы модулей, настраиваемые правила комментатора, игровые данные и секреты хранятся раздельно. При обновлениях программы не допускается стирание действующих профилей, рассадок или истории раздач.
6. **Безопасность эфира важнее новых функций:** обновление, импорт темы, ИИ-запрос или ошибка GitHub не должны останавливать запись/трансляцию и ломать уже опубликованные плашки.

### Каталог модулей и владельцы ответственности

| Модуль / область | Ответственность | Допустимая самостоятельная доработка |
|---|---|---|
| `hi_jack_core` / HI, JACK CORE | Жизненный цикл, API, события, менеджер модулей, совместимость, диагностика | Только после проверки всех потребителей контрактов |
| `hj_players` / HJ PLAYERS | Игроки, дилер, физические боксы, статусы, плашки и раскладки | Да, через объявленный интерфейс CORE |
| `hj_timer` / HJ TIMER *(предлагаемая граница)* | Турнирный таймер, время эфира, параметры показа | Да, после фиксации API и подтверждения фактического имени модуля |
| `hj_effects` / HJ EFFECTS | Темы, анимации, звук, визуальные эффекты | Да, с проверкой совместимости браузерных источников |
| OBS-интеграция | `obs-websocket`, сцены, источники, камеры и связь | Да, при стабильном публичном API |
| `hj_vision` / HJ VISION | Анализ изображения и предложения событий | Да, без прямого неконтролируемого управления эфиром |
| `hj_ai_commentator` / JACK AI | Подсказки и комментарии, личность, обучение и синхронизация правил | Да, включая независимый `JACK AI TRAINING SYNC` |
| HJ HIGHLIGHTS / AUTO RECAP | Повторы, сохранение эпизодов, подбор и подготовка клипов | Да, через OBS и шину событий |

Имена каталогов, ещё не подтверждённые фактическим деревом исходников, указаны как **проектные обозначения**. Переименовывать существующие папки без анализа зависимостей нельзя.

### Минимальный контракт автономного модуля

- `manifest.json` или эквивалент: ID, версия, совместимый диапазон CORE/API, зависимости, хэши пакета при необходимости.
- `README.md`: назначение, запуск, настройка, типичные ошибки, ограничения.
- `API.md` и/или `EVENTS.md`: публичные методы, события, схемы сообщений, правила обратной совместимости.
- `tests/`: минимум критические модульные и smoke-тесты.
- `CHANGELOG.md`: что изменено и требуется ли миграция данных.
- Явное разделение **модуля**, **устанавливаемых ресурсов**, **пользовательских данных** и **секретов**.

**Правило контракта:** нельзя молча изменять общую структуру API или форматы событий. Несовместимые изменения требуют новой версии контракта, тестов интеграции и согласования в центральном чате проекта.

## 3. Дорожная карта HI, JACK LIVE 1.0

### Этап 1. Стабильная Windows-программа — первый приоритет

**Содержание:** проверить запуск, реакцию всех кнопок, управление десятью игроками, смену режимов, корректное закрытие, сохранение и восстановление настроек. Исключить зависания окна и проблемы фонового сервера. Внедрить системный трей, понятную диагностику, возможность перезапуска локального сервера.

**Сборка и поставка:** GitHub Actions должен выполнять тесты и Windows-сборку, после чего предоставлять готовый архив. Пользовательский сценарий: **скачать → распаковать → запустить**, без установки Python, ручной сборки EXE и правки файлов.

**Приёмка:** тест на реальном Windows-компьютере пройден без зависаний; 10 игроков добавляются; плашки, таймер и время управляются корректно; после перезапуска настройки сохранились; подтверждена установка официального ZIP и диагностический сценарий при ошибке.

**Статус:** в проверке; стабильность не подтверждена.

### Этап 2. Независимая модульная архитектура

**Содержание:** завершить HI, JACK CORE, менеджер модулей, публичные API, шину событий и отделение файлов каждого модуля. Поддержать версионирование, предварительную проверку ZIP, резервную копию и откат.

**Обязательный реальный тест:** обновить **только `hj_players`** через ZIP без замены других каталогов; убедиться, что рассадка и профили остались прежними; затем проверить штатный откат при искусственно вызванной ошибке обновления.

**Приёмка:** для следующей доработки достаточно передать в отдельный чат папку одного модуля вместе с его контрактами; CORE и остальные модули работают без изменений.

**Статус:** основа заявлена, независимость должна быть доказана испытанием.

### Этап 3. HJ PLAYERS — готовность к эфиру

**Содержание:** игроки и дилер; привязка к физическим боксам; статусы, замены и скрытие плашек; свободное перетаскивание каждой плашки поверх реального кадра камеры; собственный размер и позиция у каждой плашки. Редактор с направляющими, отменой действий, предварительным просмотром и явной публикацией раскладки. Профили под разные камеры и ракурсы.

**Уточнение по текущей разработке:** превью должно соответствовать горизонтальному кадру **16:9**, включая использование камеры DJI Osmo Pocket 3. После выбора бокса плашке можно назначить начальную позицию автоматически, но оператор всегда вправе скорректировать её вручную. Координаты должны сохраняться в выбранном профиле и **фактически применяться в браузерном источнике OBS**; недопустима ситуация, когда редактор показывает новую позицию, а эфир — старую или центр экрана.

**Приёмка:** во время турнира можно изменить всю рассадку и опубликовать её без перезапуска OBS; изменения переживают перезагрузку приложения.

**Статус:** в разработке и тестировании; корректность публикации координат требует проверки.

### Этап 4. Премиальная графика и HJ EFFECTS

**Содержание:** довести стиль **BRONZE PREMIUM** согласно утверждённому визуальному референсу: металлические рамки, объёмные надписи, мягкое свечение, глубина и корректное масштабирование. Завершить пять сменных тем, три размера плашек и устанавливаемые пакеты оформления.

**Эффекты:** ALL-IN, DOUBLE UP, BOUNTY, WINNER, PLAYER OUT и другие состояния — с качественной анимацией, звуком и безопасным запуском/остановкой в OBS.

**Приёмка:** эффекты и плашки смотрятся как готовая графика реального эфира, а не тестового интерфейса; тематика не ломает рассадку или масштабирование.

**Статус:** требуется дальнейшая доводка.

### Этап 5. Полная интеграция с OBS

**Содержание:** подключить `obs-websocket`, определять текущую сцену, переключать профили при смене камер, получать кадры/превью камер, управлять видимостью источников и оверлеев. Контролировать состояние соединения и задержки переключения.

**Приёмка:** смена сцен, видимость графики и восстановление связи работают предсказуемо во время записи и прямого эфира.

**Статус:** реализация не подтверждена как завершённая.

### Этап 6. HJ VISION

**Содержание:** компьютерное зрение для анализа покерного стола — карты, действия, игровые события только в пределах достижимой точности и видимости камер.

**Приоритет безопасности:** первоначально HJ VISION только **предлагает** событие оператору. Автоматический запуск статусов и эффектов допускается после измерения точности, регистрации ошибок и утверждения порогов качества.

**Приёмка:** оператор видит обоснованное предложение, может подтвердить или отклонить его; ложное распознавание не должно самостоятельно изменять эфир.

**Статус:** план развития.

### Этап 7. JACK AI — комментатор и голосовое обучение

**Содержание:** развить начатый OpenAI-модуль: голосовой ввод заданий, управление характером и манерой комментирования, память только о подтверждённых игровых событиях, голосовая корректировка нежелательных реплик, режим обучения, предпросмотр комментариев и контролируемая озвучка в OBS. API-ключ хранится локально и не передаётся в GitHub.

**Важное обязательное дополнение:** реализовать `JACK AI TRAINING SYNC` по разделу 4 этого документа — независимое обновление правил комментатора из отдельного GitHub-репозитория без пересборки приложения.

**Приёмка:** реплики создаются на основе утверждённых правил и разрешённого игрового контекста, перед эфиром доступны предпросмотр и управление; обновление/откат правил не нарушает работающий эфир.

**Статус:** функциональность JACK AI начата; TRAINING SYNC — ТЗ принято, готовность не подтверждена.

### Этап 8. HJ HIGHLIGHTS / AUTO RECAP

**Содержание:** сохранение событий через OBS Replay Buffer (крупные банки, выбивания и другие отмеченные моменты); затем автоматический отбор лучших эпизодов, сборка коротких обзоров и подготовка вертикальных роликов для соцсетей Hi, Jack Club.

**Приёмка:** событие можно отметить во время эфира и безопасно сохранить повтор; итоговые нарезки не вмешиваются в текущую трансляцию.

**Статус:** план развития.

## 4. Дополнение № 5 — JACK AI TRAINING SYNC

### 4.1. Цель и принцип

Обучать ИИ-комментатора через **ChatGPT-проект, в том числе голосом**, утверждать изменения естественным языком, публиковать проверенный набор правил в отдельном GitHub-репозитории **`hi-jack-ai-training`**, после чего загружать его кнопкой в HI, JACK LIVE. **Никакой пересборки EXE или замены папки `hj_ai_commentator` для обновления только правил.**

Обучение в этой архитектуре означает обновление декларативных инструкций, примеров и тестов поведения, а **не дообучение весов модели**. Сам факт голосового разговора не меняет правила: публикация возможна только после явного подтверждения пользователя и успешной записи в GitHub через подключённый доступ с нужными разрешениями.

### 4.2. Раздельные источники данных

| Источник | Хранит | Не должен хранить |
|---|---|---|
| Репозиторий `hi-jack-ai-training` | Версионированные правила личности, стиль и частоту реплик, юмор, правила анализа покера, хорошие и плохие примеры, тест-кейсы, changelog | API-ключи, пароли, персональную историю раздач, рабочую базу клуба |
| Код `hj_ai_commentator` | Загрузчик и валидатор правил, механизм генерации, интерфейс обучения, тестовый режим, интеграционные адаптеры | Произвольно зашитые изменяемые правила как единственный источник истины |
| Локальные данные HI, JACK LIVE | Игровые профили, подтверждённые события, история раздач, статистика, сохранённая версия правил, резервные копии | Публичные секреты и незашифрованные токены доступа |

### 4.3. Что можно менять в обучающем наборе

- Личность и характер JACK AI, допустимая манера общения.
- Стиль, допустимую эмоциональность, длину и **частоту** комментариев.
- Удачные примеры реплик и нежелательные формулировки.
- Границы юмора, ситуации, когда шутки неуместны.
- Правила анализа покерных ситуаций с обязательным учётом неопределённости.
- Тестовые игровые ситуации, ожидаемое поведение и стоп-сценарии.

### 4.4. Подтверждение и публикация из ChatGPT

1. Пользователь в отдельном чате JACK AI описывает голосом или текстом желаемую коррекцию.
2. ChatGPT формирует **предложение**, показывает изменённые правила, примеры и возможные последствия.
3. Пользователь явно утверждает конкретную редакцию изменений.
4. При доступном и авторизованном GitHub-подключении изменения сохраняются в отдельную ветку/PR либо утверждённую версию `hi-jack-ai-training` по согласованной процедуре. Отсутствие доступа не выдаётся за успешную публикацию.
5. Выполняются проверки структуры и тестовых сценариев; публикация сопровождается номером версии и журналом изменений.
6. Приложение обнаруживает подтверждённый выпуск, но **не обязано автоматически применять** его без действия оператора.

### 4.5. Синхронизация в приложении

Раздел интерфейса **JACK AI → Обучение** должен показывать текущую локальную версию, дату обновления, наличие новой утверждённой версии и список изменений. Кнопки:

- **ОБНОВИТЬ ПРАВИЛА ИЗ GITHUB** — получить доступную версию и применить её после проверки.
- **ОТКАТИТЬ ПРАВИЛА** — безопасно вернуться к ранее успешно активированной версии.
- **ПРОВЕРИТЬ ДЖЕКА** — тестовые комментарии по предустановленным сценариям без вывода звука в эфир.

**Транзакция обновления:** соединение с GitHub → получение манифеста утверждённого выпуска → сравнение версий → загрузка в отдельную временную папку → проверка целостности, структуры и совместимости → автоматические сценарии → резервное копирование предыдущего пакета → атомарное переключение активной версии → отображение результата. При сбое действующий пакет остаётся без изменений.

**Поведение в эфире:** уже начатый комментарий может завершиться с прежней версией правил; новая версия применяется только к новым запросам комментатора. Обновление не должно прерывать запись/трансляцию, менять данные игроков или воздействовать на сторонние модули.

### 4.6. Защита и надёжность

- Приватный репозиторий допускается; для скачивания использовать GitHub API с **минимальными правами чтения**. Права записи нужны только авторизованному процессу публикации правил, не эфирному приложению.
- Токены — в защищённом хранилище Windows (например, Windows Credential Manager/DPAPI); ключи и токены не помещать в исходники, YAML/JSON правил, ZIP, диагностические логи и скриншоты.
- Не исполнять загружаемые правила как произвольный код. Предпочтительны валидируемые декларативные JSON/YAML и проверенные схемы.
- Проверять доверенный источник и конкретный коммит/релиз; SHA-256 подтверждает целостность скачанного файла, но сам по себе **не подтверждает подлинность источника**.
- При отсутствии интернета и GitHub всегда использовать **последнюю успешно установленную** версию. Повреждённые и несовместимые комплекты отклонять.
- Хранить доступный для отката проверенный пакет, результат тестов и запись о времени перехода; откат не должен менять историю игр.

### 4.7. Контракт версии обучения — проектное предложение

Рекомендуется метаданные каждого выпуска хранить в `training-manifest.json` с полями: `training_version`, `min_module_version`, `max_module_version` (или диапазон), `schema_version`, `release_commit`, `files` с контрольными суммами, `changelog`, `tests`. ## 5. Регламент разработки по отдельным чатам ChatGPT

**Основной принцип:** один модуль — один специализированный чат. Этот чат проекта — **центральный штаб** для архитектуры, дорожной карты, версии приложения, решения конфликтов и ежедневного статуса.

**В центральном чате:** фиксируются общие требования, архитектурные решения, совместимость, результаты интеграционных испытаний, приоритеты и готовность релизов. Здесь не следует считать функцию реализованной только потому, что она обсуждена в другом чате.

**В чате модуля:** передаются ID/версия модуля, его папка/репозиторий, README, API/EVENTS, границы разрешённых изменений и критерии приёмки. Изменения делаются только внутри указанной области, если не согласовано другое.

**Типовой цикл:**

1. Зафиксировать задачу и версию исходного кода (ветка/commit SHA/ZIP), от которой начинается работа.
2. Проверить фактическую структуру модуля и общие контракты; не придумывать отсутствующие файлы/API.
3. Реализовать изменение; обновить документацию и тесты только затронутого модуля.
4. Выполнить модульные проверки, затем интеграционные проверки с CORE/OBS там, где они необходимы.
5. Опубликовать ветку и PR в GitHub или предоставить версионированный ZIP при согласованном офлайн-процессе. Не вносить изменения прямо в защищённую стабильную ветку без принятия.
6. Установить тестовую сборку/ZIP, сохранить резервную копию, проверить миграцию пользовательских данных и штатный откат.
7. Передать в центральный чат короткий отчёт: коммит/релиз, что поменялось, какие тесты пройдены, что осталось непроверенным и как откатиться.

**Ограничения:** разные чаты не обладают гарантированно общей живой памятью и не синхронизируют автоматически свои изменения. Источником состояния служат **GitHub, версионированная документация, релизные артефакты и подтверждённые испытания**. ZIP удобен как формат поставки одного модуля, GitHub нужен для истории, конфликтов, обзора изменений, тестов и восстановления.
